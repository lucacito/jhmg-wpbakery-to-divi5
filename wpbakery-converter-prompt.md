## What stays the same

Rename the namespace to `WPBakeryDivi5Converter\`, the slug to `jhmg-converter-for-wpbakery-to-divi` (Pro: `-pro`, product slug `wpbakery-to-divi5-pro`), and the global prefix to `wbdc_` / `WBDC_` (Pro `wbdcp_` / `WBDCP_`). The prefix must be at least four characters: WordPress.org rejects shorter ones and Plugin Check discards them. Install Plugin Check in the Docker setup script from day one, add `scripts/plugin-check.sh`, and keep the free plugin at zero findings.

Carry over every rule in the Beaver `CLAUDE.md`: never scrape HTML, Divi attribute paths only from the Divi source (`references/Divi.zip`, 5.12.1), gradient stop positions without units, icon settings written `unicode, type, weight`, flex columns sized with `module.decoration.sizing.flexType` on the 24-grid, nested rows for inline groups, every handler calls `logUnmappedSettings()`, colours never invented, expected fixtures as reviewed goldens, real-world exports must convert validator-clean with zero skipped settings, `vendor/bin/phpunit` and Playwright before any claim of success, version in every place checked by a test.

## What is different about WPBakery

WPBakery stores the layout as shortcodes in `post_content`, not in post meta: `[vc_row][vc_column width="1/2"][vc_column_text]…[/vc_column_text][/vc_column][/vc_row]`, with `vc_row_inner` / `vc_column_inner` for nesting. A page is a WPBakery page when post meta `_wpb_vc_js_status` is `true`. Per-page design CSS lives in post meta `_wpb_shortcodes_custom_css` (and `_wpb_post_custom_css`) as rules like `.vc_custom_1600000000000{margin-top: 20px !important;background-color: #f5f5f5 !important;}`, referenced from elements by their `css` attribute. Parse those rules directly into spacing, backgrounds and borders. `vc_raw_html` content is urlencoded then base64-encoded. `vc_custom_heading` packs its typography into `font_container` (`tag:h2|font_size:30px|text_align:left|color:%23ffffff|line_height:1.2`) and `google_fonts`. `vc_btn` uses a named colour palette, `style`, `shape`, `size`, `i_icon_fontawesome` and a packed `link` (`url:…|title:…|target:…|rel:…`). Column widths are twelfths, including 5/12, 7/12 and 11/12, which need the flex-group fallback the Beaver converter already has. Rows carry `full_width` (`stretch_row`, `stretch_row_content`, `stretch_row_content_no_spaces`), `gap`, `equal_height`, `content_placement`, `parallax`, `video_bg`, `css_animation`, `el_class`, `el_id`. Columns carry `offset` classes (`vc_col-lg-…`, `vc_hidden-xs`) for responsive width and visibility.

WPBakery is a paid plugin, so it is not on WordPress.org. Ask me for the `js_composer` zip and put it in `references/` like Beaver Lite; take every element's parameters from its source (`include/templates/shortcodes/*.php`, `include/classes/shortcodes/`, `include/params/`), including the named colour palette, and write `docs/wpbakery-schema.md` from it. WPBakery ships a bundled template library; use those templates as fixtures. WordPress.org exports (WXR) carry the shortcodes in `content:encoded`, so the import parser reads that.

The big real-world fact: most WPBakery sites run a ThemeForest theme (Salient, Bridge, The7, Jupiter, BeTheme and others) whose own shortcodes sit inside the WPBakery layout, plus add-ons such as Ultimate Addons for WPBakery (`ultimate_*`) and Massive Addons. Treat those like the Beaver converter treats add-on settings: known families classified and reported once per node, and unknown shortcodes never dropped silently. When converting a page on the same site, render an unknown shortcode with `do_shortcode()` into a static `divi/code` block and report it as a static copy, the way the Beaver Widget and WordPress Patterns handlers do; when converting from an export, leave a labelled placeholder that keeps the text.

## Mapping to start from

`vc_row` → `divi/section` (stretched rows → full-width), `vc_row_inner` → nested `divi/row`, `vc_column` → `divi/column`, `vc_column_text` → `divi/text`, `vc_custom_heading` → `divi/heading`, `vc_single_image` → `divi/image`, `vc_btn` → `divi/button`, `vc_icon` → `divi/icon`, `vc_separator` → `divi/divider`, `vc_text_separator` → heading plus divider, `vc_empty_space` → invisible `divi/divider` with the height, `vc_tta_accordion` → `divi/accordion`, `vc_tta_tabs` and `vc_tta_tour` → `divi/tabs`, `vc_toggle` → `divi/toggle`, `vc_gallery` → `divi/gallery`, `vc_images_carousel` → `divi/slider`, `vc_video` → `divi/video`, `vc_gmaps` and `vc_raw_html` and `vc_raw_js` → `divi/code`, `vc_progress_bar` → `divi/counters`, `vc_pie` → `divi/circle-counter`, `vc_message` → styled `divi/text`, `vc_cta` → `divi/cta`, `vc_hoverbox` → `divi/blurb`, `vc_basic_grid` / `vc_masonry_grid` / `vc_posts_slider` → `divi/blog` or `divi/post-slider`, `vc_wp_*` → the widget rendered with `the_widget()` into `divi/code`, social and chart elements → reported placeholders. Verify every one against Divi's `module.json` before writing it.

Reproduce WPBakery's box model rather than Divi's defaults, as the Beaver converter does for Beaver's: WPBakery rows use negative-margin gutters with 15px column padding, the `gap` attribute changes them, and section padding comes from the theme. Decide the defaults with side-by-side screenshots on the Docker site before writing the StyleMapper, and record the decision in `CLAUDE.md`.
