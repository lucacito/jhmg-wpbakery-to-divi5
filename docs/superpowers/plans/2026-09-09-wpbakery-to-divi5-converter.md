# WPBakery Page Builder → Divi 5 Converter Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship a free WordPress plugin (plus a Pro add-on) that converts WPBakery Page Builder pages into native Divi 5 block pages, with a check-before-convert report, undo, tests gated by the Divi 5 deterministic validator, a Docker environment, Plugin Check at zero findings, and the divi5lab.com product wiring.

**Architecture:** A pure-PHP pipeline mirrors the Beaver Builder converter: `ShortcodeParser` (WordPress shortcode grammar) + `AttributeNormaliser` (both WPBakery attribute eras) → `NodeTree` → `ConverterEngine` dispatching per-tag handlers through a registry, with `StyleMapper` translating WPBakery design-options CSS rules and packed parameters to Divi 5 attribute paths → `DiviBlockSerializer` emitting `<!-- wp:divi/* -->` blocks → `DiviExporter` writing the post. Preflight/plan/commit keeps every write behind an explicit Convert click; `ImportHistory`/`ImportRollback` make it undoable. Everything not WPBakery-specific is ported from `../jhmg-beaver-to-divi5` with the rename table below.

**Tech Stack:** PHP 8.0+ (WordPress plugin, no runtime deps), PHPUnit 13 with WP function stubs, Playwright 1.44+ + Docker (WordPress php8.3 + MySQL 8) for end-to-end, Divi 5 Deterministic Validator (vendored, pure PHP) as an output gate, WordPress Plugin Check.

**Spec:** `docs/superpowers/specs/2026-09-09-wpbakery-to-divi5-converter-design.md` (read it first; section numbers below refer to it)

## Global Constraints

- Plugin slugs/text domains: `jhmg-converter-for-wpbakery-to-divi` (free), `jhmg-converter-for-wpbakery-to-divi-pro` (Pro). Namespaces `WPBakeryDivi5Converter\` / `WPBakeryDivi5Converter\Pro\`. Global prefixes `wbdc_`/`WBDC_` (free) and `wbdcp_`/`WBDCP_` (Pro) on every hook, option, transient, post meta, constant, nonce and form field. Admin CSS classes `wbdc-`. Never shorter than four characters.
- Requires PHP 8.0, WordPress 5.9; converter output requires Divi ≥ 5.0.0 (`DiviRequirement`). `Tested up to` is read off the Docker container, never carried forward.
- Never modify the source WPBakery post. Conversions always create a new post.
- Never scrape HTML. Read `post_content` (shortcodes) and the metas `_wpb_vc_js_status`, `_wpb_shortcodes_custom_css`, `_wpb_post_custom_css` only.
- Divi attribute paths only as read from `references/Divi.zip` (Divi 5.12.1): `Divi/includes/builder-5/visual-builder/packages/module-library/src/components/<module>/module.json` and `server/Packages/StyleLibrary/Declarations/`. Every path a task writes is recorded in `docs/divi5-schema.md` (Task 15). Do not invent block types or attribute shapes.
- WPBakery field names only as read from `references/js_composer.9.0.1.zip` (`config/**`, `include/templates/shortcodes/*.php`, `include/classes/shortcodes/*.php`, `include/params/**`, `include/classes/migrations/class-wpb-template-attributes-migration.php`) and `references/js_composer.7.8.zip` for the pre-9.0 forms; Ultimate Addons fields from `references/Ultimate_VC_Addons.zip` (`modules/*.php`).
- Gradient stop positions are bare numbers (`"23"`, never `"23%"`). Icon settings are written `unicode, type, weight` in that order. Colours are never invented: unknown palette names are reported under `unresolved_globals`.
- Every handler calls `logUnmappedSettings()` with every key it consumed; nothing is dropped silently. Handlers are written to the 9.0.1 attribute names; the normaliser converts pre-9.0 forms first.
- Expected fixtures are reviewed goldens: `php scripts/render-fixture.php fixtures/wpbakery/<name>.txt --report`, read the output, then `php scripts/update-expected.php <name>`.
- Before claiming anything works: `vendor/bin/phpunit`; `npx playwright test` when the Docker site is up; `scripts/plugin-check.sh free` at zero findings before a release. Report failures with output.
- Free converts one item per run (`wbdc_direct_conversion_limit` default 1); Pro raises it. `wp_update_post`/`wp_insert_post` content is `wp_slash()`ed.
- Version lives in three places for free (plugin header, `WBDC_PLUGIN_VERSION`, readme `Stable tag`) and two for Pro; tests assert they agree. Both start at 1.0.0.
- Commit after every task with the conventional messages the sibling repos use (`feat(parser): …`, `test(e2e): …`, `docs: …`), ending with `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`. Nothing outward-facing (push, deploy, Stripe objects) without an explicit go-ahead.
